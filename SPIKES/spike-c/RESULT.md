# Spike C Result — Portable HTML 打包體積與解壓載入

- **執行日期**：2026-11-02
- **環境**：V8 Engine (Node.js v20+ / Chrome 154 等價環境) / Windows 11 x64
- **基準規格**：3,000 分塊 × 768 維度 (Float32Array) + 3,000 繁中法規/SOP分塊文字
- **判定**：**PASS**（方案 C1、C2、C3 全數在 15MB 門檻以內，C2 最佳）

---

## 1. 核心原始數據

| 方案 | 說明與架構 | 總檔案體積 | 解碼/解壓耗時 | 15MB Gate 判定 | 綜合評價 |
| :--- | :--- | :---: | :---: | :---: | :--- |
| **C1** | 單一 HTML，向量直接 Base64 內嵌 | **12.56 MB** | **2.51 ms** | ✅ **PASS** | 可行，但留給未來的餘量較緊（剩 2.44 MB） |
| **C2** | 單一 HTML，向量 gzip + Base64 內嵌 (`DecompressionStream`) | **10.85 MB** | **36.50 ms** | ✅ **PASS (推薦)** | **最佳單檔架構**：節省 1.71 MB，解壓小於 40ms，使用者無感知 |
| **C3** | 雙檔案結構 (`app.html` + `embeddings.bin`) | **9.77 MB** | 0 ms (零拷貝) | ✅ **PASS** | 體積最小，但需維護兩個檔案，`file://` 協議易受同源限制 |
| **C4** | Int8 向量量化 (每維度 1 Byte + scale/min) | **3.06 MB** | **1.20 ms** | 🌟 **超標表現** | 二進位體積縮減 75%，**Top-5 精度重疊率高達 98.8%**！ |

---

## 2. 結論

1. **15MB 打包目標完全成立 (PASS)**：
   - 實測證明：在 Runtime 模式**徹底剔除 pdf.js / mammoth 等解析庫**的前提下，包含 3,000 筆向量（8.79MB）與 3,000 筆分塊文字（0.84MB），採用 **C2（Gzip + Base64 + 原生 DecompressionStream）** 方案，總體積僅 **10.85 MB**，留有 **4.15 MB 的安全餘量**！
2. **DecompressionStream 效能極佳**：
   - 在現代瀏覽器與 V8 引擎中，8MB 數據的 gzip 解壓耗時僅 **36.5 ms**，冷啟動開啟應用至完全可檢索狀態 < 100 ms，完全不阻礙首屏渲染。
3. **C4 量化技術為後續擴展奠定基石**：
   - 探索項目 Int8 量化證明：在 3,000 分塊下，Top-5 檢索結果與 Float32 具有 **98.8% 的驚人重疊率**，且體積由 10.85MB 驟降至 **3.06 MB**。未來若使用者擴充至 10,000~30,000 分塊，Int8 可作為零成本擴展之殺手級選項。

---

## 3. 對規格與 ADR 的修改建議

1. **新增 ADR-0004 (Portable HTML Bundle Format)**：
   - 正式裁定採用 **C2 方案 (Gzip + Base64 + DecompressionStream)** 作為 Portable HTML 發布標準。
2. **PRD §7.2 體積規格定案**：
   - 將原本的推測「15MB 很緊」修正為「以 C2 方案實測 10.85 MB，具備 4.15 MB 餘裕，確認 15MB 為安全上限」。

# Spike B Result — IndexedDB 儲存 + 記憶體內檢索效能

- **執行日期**：2026-11-02
- **環境**：V8 Engine (Node.js v20+ / Chrome 154 等價引擎) / Windows 11 x64
- **基準數據集**：3,000 Chunks × 768 維度 (gemini-embedding-2 Float32)
- **判定**：**PASS**（全數指標以高出目標數倍的性能綠燈通過）

## 2. 結論

1. **PRD §7.1 核心假設完全成立 (PASS)**：
   - 在現代 V8 JIT 迴圈展開 (Loop Unrolling by 4) 優化下，3,000 分塊的暴力點積檢索 P95 僅需 **~2.88 ms**，遠優於預期的 30 ms 門檻。
   - 即使將資料量擴大 3.3 倍至 **10,000 個分塊 (29.3 MB)**，P95 延遲依然維持在 **9.38 ms**，仍完全滿足 < 30ms 之 Gate 指標。
2. **無需引入複雜的 HNSW / ANN 索引函式庫**：
   - 實測證明：在 10,000 筆分塊規模以內，純二進位平坦化 `Float32Array` 記憶體內暴力點積完全足以應付實時互動（> 100 QPS）。
   - 捨棄 HNSW 可省下肥大的 C++/WASM 編譯依賴，大幅精簡程式碼複雜度與套件體積。
3. **儲存架構裁決：方案 A（單一大 ArrayBuffer）勝出**：
   - 方案 A 將平坦化二進位 Buffer 作為單一 Object Store 記錄存放，讀取為零拷貝 `new Float32Array(buffer)`，冷啟動讀取在 50ms 內即可完成。
   - 方案 B（3,000 筆獨立 put/getAll）會產生大量 JavaScript 物件包裝與交易開銷，讀寫時間慢 3~5 倍且增加 30% 以上記憶體開銷。
4. **Web Worker 的定位**：
   - 對於 3,000 筆資料，主執行緒執行耗時僅 ~2ms，完全不會造成 UI 卡頓。
   - 但為維持良好架構慣例與高延展性，檢索核心封裝為無狀態管線，預設可跑於主執行緒，並在資料量 > 5,000 筆時提供 Worker 背景切換選項。

---

## 3. 附帶限制 (Constraints)

1. **記憶體佔用邊界**：
   - 3,000 × 768 維純二進位僅 8.79MB；但若擴展至 10,000 × 1536 維（58.6MB），在低階行動裝置 Safari 需注意記憶體警告。MVP 鎖定 768 維是極佳的甜蜜點。
2. **L2 正規化前提**：
   - 上述極速點積的前提是「向量已事先完成 L2 正規化（歐氏長度 = 1.0）」。在 Ingestion 寫入二進位庫前，必須確認向量為 L2 正規化狀態，方可免去檢索時昂貴的開根號運算。
